# 06 实施与分层验收（Iteration & Validation）

目标：把提案变成实际改动，并且**拿出证据**证明改对了——或者诚实地说没改对。

这一环决定了这个 Skill 是"分析报告生成器"还是"能推动产品进步的工作系统"。

---

## 一、开工前

1. **锁定范围**：本轮只做 1 个主目标。范围写成一句话，超出范围的想法记进 Backlog，不顺手做。
2. **写死验收标准**：一条可观察的判据，例如"新用户从打开到拿到第一份结果 ≤ 3 步"、"新建报表时能看到已有数据源并可一键引入"。
   - 不接受"交互更流畅""体验更好"这类标准。
   - 标准要在动手前写，不是做完后补。
3. **定回退方式**：改哪几个文件、是否有数据迁移、怎么回到原状。涉及数据结构或用户数据的，先确认再动。
4. **先取基线**：动手前把"改前"的数字测出来。取不到基线，后面的对比就是空的。

```bash
# 最少也要有的三样
git rev-parse --short HEAD                 # 改动起点
git status --short                          # 确认工作区干净，避免混入无关改动
# 加一条可重复执行的观测命令（重走路径时跑同一句）
```

基线写进 `templates/iteration-report.md` 的"改前"列。**没取基线就开始改，是这一环最常见的失误**——改完只能写"已完成，效果未测量"。

## 二、实施中

- **小步**：一次改动一个可独立验证的点，改完立刻自检，不要一次改十个文件再看。
- **先保护**：不动与目标无关的既有能力；不顺手重命名、不顺手换风格。
- **不擅自做**：批量数据迁移、删除用户数据、改认证/付费/权限逻辑、覆盖用户已有文档。
- **遵守权限级别**：L2 未经确认不动手；L3 只提案。
- 遇到原方案行不通：停下来说明，不要为了完成计划硬凑一个次优实现。

## 三、分层验收

按四层走，前一层不过不进下一层。

### 工程层（必须有命令和输出）

```bash
# 按项目实际情况挑
npm run build && npm run test
pytest -q
tsc --noEmit
```

记录：命令、结果、是否有回归。跑不了测试就说明原因，不要写"代码看起来没问题"。

### 体验层（重走同一条路径）

用 02 里记录的**同一条路径**重走一遍，逐项对比：

| 指标 | 改前 | 改后 |
|---|---|---|
| 完成核心任务步数 | 7 | 4 |
| 需要看文档才能继续的环节 | 2 | 0 |
| 卡点（犹豫/找不到） | 3 处 | 1 处 |
| 错误路径下的可恢复性 | 无提示，数据丢失 | 有明确提示，可撤销 |

数字和具体现象都要。截图/录屏/日志比形容词有说服力。

**拿不到界面时的代理指标**：改不了 L-a，就用这些替代，并在结论里降到对应可信度。

| 原指标 | 代理指标（L-b/L-c 可取） |
|---|---|
| 用户点几次 | 请求数（一个动作打几次接口） |
| 页面跳转次数 | 路由切换次数（日志/埋点） |
| 卡点 | 报错次数 + 需要重试的次数 |
| 可恢复性 | 构造失败输入后，数据是否仍在、是否有错误码与提示文案 |
| 是否"显得快" | 关键接口耗时 / 渲染前等待时间 |

**验收证据清单**（缺一项就不算完成体验层）：

- [ ] 同一条路径的改前 / 改后记录（放同一张表）
- [ ] 至少 1 条可复现的对比事实（命令输出、截图、日志片段）
- [ ] 工程检查的命令与结果
- [ ] 引入的回归项检查结果（必须检查，不能默认"没有"）
- [ ] 未验证部分的明确声明

### 产品层（判断方向对不对）

- 是否更贴近产品核心定位？
- 是否让目标用户更快得到价值，而不是让功能更好看？
- 是否引入了新的复杂度、新的概念、新的维护负担？
- 是否创造了新的"必须学一下才会用"的东西？

诚实回答"引入了一点复杂度但换来了明确的启动成本下降"是可以的；说"零成本提升"通常是在自欺。

### 真实用户层（只能给方案，不能给结论）

我们做不到真实用户研究。这一层只能：

- 提出验证方案（找几个用户、看什么行为、什么算通过）。
- 如果用户自己提供了真实反馈，如实引用并标明来源。
- 明确写"本轮未获得真实用户验证"。

**不允许**：用角色模拟的推演当作"用户反馈"，或写"用户应该会喜欢"。

## 四、验收结论三态

| 结论 | 含义 | 后续 |
|---|---|---|
| **达成** | 验收标准全部满足，有证据 | 更新档案，选下一项 |
| **部分达成** | 主目标改善但标准未全满足 | 写清差在哪、为什么、是继续还是换方案 |
| **未达成** | 标准没达到，或引入回归 | 回退或重新归因，**必须写进 DECISION_LOG** |

未达成不是失败，隐藏未达成才是。记录未达成的原因，是后续迭代最有价值的信息。

**本轮无法验证怎么办**：写明"改动已完成，验证未执行 + 原因 + 补验证的条件"，结论记为"部分达成（仅工程层）"。不得因为改动确实做了，就默认写"达成"。

## 五、写 ITERATION_LOG

用 `references/templates/iteration-report.md`，必备六项：

1. 本轮目标（一句话）与验收标准
2. 实际改动（文件级清单 + 行为变化）
3. 验收证据（命令输出 / 前后对比 / 截图路径）
4. 结论（达成/部分达成/未达成）
5. 遗留问题与新增发现
6. 下一轮建议（1 条）

同时更新：

- `DECISION_LOG.md`：本轮采纳/拒绝的判断及理由
- `OPPORTUNITY_BACKLOG.md`：新产生的假设、已关闭的假设
- `PRODUCT_PROFILE.md`：只有产品定位、用户、能力清单真的变了才改

## 六、多轮节奏

一轮结束提三个问题，决定下一轮：

1. 这一轮改变用户的实际行为了吗？（未必能量化，但要能说出预期变化）
2. 有没有出现新的、更痛的问题？（有的话下一轮优先它）
3. 当前最该做的是继续优化体验，还是回到方向层？（连续三轮都在做局部优化，通常说明方向没解决）

---

## 退出条件

- [ ] 验收标准在动手前已写
- [ ] 工程层有命令与输出
- [ ] 体验层有前后对比
- [ ] 结论是明确三态之一，未达成未被掩盖
- [ ] ITERATION_LOG / DECISION_LOG 已更新
- [ ] 没有做超出范围或超出权限的改动

## 常见失败

- 改完直接说"已优化完成" → 没有证据，是三个失败信号之一。
- 顺手重构一大片 → 无法判断是哪一步产生了效果。
- 验收标准事后补写，且写得刚好达成 → 自评闭环，等于没验收。
- 未达成就换个说法叫"部分达成" → 掩盖问题，后续会重复踩坑。
