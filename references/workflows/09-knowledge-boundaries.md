# 09 知识边界（三级隔离）

## 目的只有三个

拦三种错误，别的一概不管：

1. 把**一次观察**写成**普遍规律**。
2. 把**一个提案**写成**用户已经做出的决定**。
3. 把**一个项目的经验**变成**所有项目都适用的方法**。

**这不是审批系统。** 判断成本上限：每条记录 10 秒、写一个状态词。除了"已否决/已作废"要写一行理由，其余不写理由、不写评审意见、不建待审队列。

---

## 一、三层

| | **L1 技能知识** | **L2 项目知识** | **L3 会话上下文** |
|---|---|---|---|
| 位置 | 本技能包（SKILL.md、references/） | `<项目根>/product-evolution/` | `<项目根>/product-evolution/sessions/<时间>/` |
| 只放 | 跨产品通用的方法、判据、模板 | 该项目的定位、用户、原则、决策、机会、迭代、假设 | 本轮观察、临时判断、未确认假设、待决策提案 |
| 绝不放 | 产品名、具体功能、单项目结论、未验证经验 | 方法论正文、未经确认的判断 | 已确认的结论（必须晋升到 L2） |
| 生命周期 | 跨产品长期 | 项目存续期 | 一轮到一次迭代，之后压缩 |

**一句话判据**：L1 是"怎么想"，L2 是"这个产品是什么"，L3 是"这次我们猜到了什么"。

## 二、十秒定位

任何一条信息落盘前，三个问题，答完就落，不辩论：

1. 换个产品还成立吗？
2. 含产品名、功能名、这个产品的数字吗？
3. 用户确认过，或有可复现的 E1 且已进入计划吗？

映射：第 1 题否 → L2 或 L3；第 2 题是 → 一定不是 L1；第 3 题否 → L3，是 → L2。
三题都过不了 → 它还不该落盘，留在对话里。

## 三、三条禁令

1. **通用包里不写产品名与项目结论。** 举例、反例都不许出现真名——真名一旦进包，后续检索会把它再次带进上下文。
2. **候选不得当依据。** `candidate` 条目可以写进项目档案、`（候选）` 方法可以留在正文，但两者都只能参考：不得当作证据引用，不得写进验收结论，不得用来支撑其他 `confirmed` 结论。
3. **技能升级不碰项目档案。** 对 `product-evolution/` 只读：不重写、不清空、不因模板变化改写历史条目；技能目录不得与项目档案目录嵌套。确需迁移时先备份到 `sessions/<时间>/backup/` 并说明理由。

## 四、L2 的四个状态

每个 L2 条目首行带一个状态词。**默认 `candidate`**，不要一上来写 `confirmed`。

| 状态 | 什么时候用 | 能否当依据 | 谁能改 |
|---|---|---|---|
| `confirmed` 已确认 | 用户明确同意；或有可复现 E1 且已进入计划 | 能 | 用户或会话 |
| `candidate` 候选 | 有依据，但未确认或未复现 | 只能参考 | 默认即此 |
| `rejected` 已否决 | 用户拒绝 | 不能，且不得重提（除非前提变化） | 用户 |
| `void` 已作废 | 被新证据推翻 | 不能，保留原文 + 推翻理由 | 会话 |

写入格式（一行，贴在条目首行）：

```
状态: candidate ｜ 证据: E1(/api/books) / E2 / E3 ｜ 反证条件: … ｜ 提出: 2026-10-30
```

只有三种动作会改状态：用户确认 → `confirmed`；用户拒绝 → `rejected`；证据推翻 → `void`。**改状态时补一行理由，其余情况不写理由。**

兼容旧词：已有档案若用 `open` / `closed`，按 `open ≈ candidate`、`closed ≈ rejected`（被推翻的算 `void`）理解，下次触碰该文件时顺手改，不专门迁移。

`DECISION_LOG` 只收 `confirmed` 与 `rejected`。`candidate` 永不进 `DECISION_LOG`——这一条就是"提案写成决定"的全部防线，不需要额外流程。

## 五、晋升 L3 → L2（自动，不评审）

满足任一条就搬，搬完在 session 里标去向：

| 触发 | 去向 |
|---|---|
| 用户明确认可某判断/方案 | `DECISION_LOG`（`confirmed`） |
| 有可复现 E1 且进入本轮计划 | `PRODUCT_PROFILE` 或 `OPPORTUNITY_BACKLOG`（`confirmed`） |
| 有依据但未确认、未复现 | `OPPORTUNITY_BACKLOG` 或 `PRODUCT_PROFILE` 对应字段（`candidate`），只作参考 |
| 做了改动并有验收证据 | `ITERATION_LOG` |
| 用户确认了长期取向 | `PRODUCT_PRINCIPLES`（带确认日期） |

`candidate` 可以进项目档案，这不算晋升——它只是"记下来了"。**只有 `confirmed` 能作为正式依据。**

不满足的留 session，标 `未晋升 + 缺什么`。这些是轮次现场，不是项目事实。

## 六、晋升 L2 → L1（四道闸，一次判断，不开会）

| 闸门 | 一行标准 |
|---|---|
| 抽象 | 去掉产品名/功能名/数字后，另一个项目能直接照做 |
| 范围 | 能说出"什么情况下不成立" |
| 验证 | ≥2 个独立产品复现，或 1 次"预判落空→被纠正→再复现" |
| 登记 | 写进 `references/method-ledger.md`，标 候选 / 已验证，附来源代号与日期 |

没打算复用的经验，不用登记——候选区是"以后可能用到"的暂存架，不是审批队列。

未过闸的内容：可以进候选区，可以留在正文但必须标 `（候选）`，**不得进 SKILL.md 当作已验证方法引用**。

## 七、跨项目

可继承：方法、判据、检查表、提问方式、模板结构。
禁止继承：结论、优先级、用户画像、定位假设、"某功能没价值"这类判断。

遇到"上个项目就是这么做的"，只能借提问方式，不能借答案。新项目重新取证，允许得出相反结论。

## 八、一轮归档（三步，顺序固定）

1. **写 session**：本轮观察、推断、假设、待决策提案全部落到 `sessions/<时间>/session-log.md`，每条带状态词。
2. **改状态 + 晋升**：够格的改 `confirmed` 并搬到 L2 对应文件；搬走的在 session 归档表标去向。
3. **登记方法**：只有"可能复用"的经验才写进 `method-ledger.md` 候选区。

只做了分析、没有实施的轮次，做完第 1 步即可，不必为凑齐步骤去改 L2。

## 九、自检（提示，不阻塞）

```bash
# 1. 通用包内不得出现已知项目名（把占位符换成实际项目名再跑，别把真名留在本文件里）
grep -rniE "PROJECT_NAME_1|PROJECT_NAME_2" SKILL.md references/ README.md
# 期望：无输出

# 2. 技能目录不应混入项目档案
ls SKILL.md PRODUCT_PROFILE.md DECISION_LOG.md 2>/dev/null | grep -E "PRODUCT_PROFILE|DECISION_LOG|ITERATION_LOG"

# 3. 项目档案是否整段转录了方法论（命中需人工看一眼：引用可以，转录不行）
grep -rn "references/workflows\|references/frameworks" <项目>/product-evolution/*.md

# 4. 会话经历标注：通用包内不得出现只对某次对话有意义的事件记录
grep -rnE "已实测|已命中|撤回|本次对话|这次实战|本轮新增|上一轮发现" SKILL.md references/ README.md
# 期望：无输出。验收案例只写规则本身，不写"这条曾经命中过"的历史。
```

两类污染都要查：**项目名词**（上面的名字表 + 领域指纹词，如具体行业的核心名词）和**经历标注**（第 4 条）。前者的教训是词表不能太窄——只查产品名会漏掉"某产品的某机制"式残留。

自检结果只做提示。命中不等于违规，违规也不阻塞工作——记一笔、继续做，下一轮修。

## 十、验收案例

| # | 输入 | 应落层/状态 | 类型 |
|---|---|---|---|
| T1 | 从某产品的一次行为观察，推断"它只把单次产出当交付物" | L3，`candidate` | 规则 |
| T2 | 用户回复"就按这个方向做" | L2 `DECISION_LOG`，`confirmed` | 规则 |
| T3 | "统计字段先读口径再解释" | L1 候选（ledger） | 规则 |
| T4 | 新项目想复用上个项目的结论 | 拒绝，只借方法 | 规则 |
| T5 | 技能升版，项目已有档案 | 只读，不改写 | 规则 |
| T6 | 本轮只分析未实施 | 只写 session | 规则 |
| T7 | 用户否决一个"很普适"的建议 | L2 `rejected`，不升 L1 | 规则 |
| T8 | 观察到某产品某接口返回空集合 | L3 观察，不得写成结论 | 规则 |
| T9 | 技能包出现产品名举例 | 违规 | 规则 |
| T10 | 项目档案粘贴整段工作流正文 | 违规 | 规则 |

## 十一、明确不做的四件事

为了让这套东西不变重，以下都不做：

- 不为每条记录写理由或评审意见；
- 不设待审清单、审批队列、双人确认；
- 不要求状态变更走流程，改一行字即可；
- 不做状态打分或优先级排序——状态是标签，不是评分。
