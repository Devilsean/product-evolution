# 05 价值判断与改进计划（Product Planning）

目标：把一堆问题和机会变成**一份用户能拍板的计划**，同时明确说出哪些不做、为什么不做。

这一环是本 Skill 最容易被跳过、也最决定成败的一环。不做判断的后果是产品被建议淹没。

---

## 一、三道硬门槛（先砍一刀）

任何提案先过：

1. **真实问题吗？** 有 E1/E2 支撑吗？只有"应该会有人需要"就不过。
2. **符合定位吗？** 让产品离核心价值更近，还是更远？变远的一律 L3，不进本轮。
3. **可验证吗？** 说不出怎么判断做对了，不过。

过不了门槛的进 `OPPORTUNITY_BACKLOG.md` 并写明"卡在哪一关"，不是直接丢弃。

### 定位一致性四问（第 2 关的操作方法）

空口判断"符合定位"没有意义，用四个问题逼出结论。答案必须来自 PRODUCT_PROFILE，不是印象：

1. **它服务的是 PROFILE 里列的目标用户吗？** 若是为另一类用户服务 → 要么改定位，要么不做。
2. **它让产品的核心价值更快到达，还是只是让功能更多？**（对照 PROFILE 的"首次价值时刻"）
3. **它是否要求用户学一个新概念、新流程、新术语？** 每新增一个，都是对现有理解成本的摊薄。
4. **如果这个功能明天被删掉，会有用户抱怨吗？** 答"不会"说明它与核心价值距离远。

四问里任何一问答案是否定的，标 L3 并说明，不进本轮实施。

### 反事实检验（防止过度乐观）

对每个候选问三句，答不上来就降级：

- **不做会怎样？** 如果什么都不做，损失具体是什么？说不出损失，就是"可以做但不值得"。
- **做了之后，用户会改变哪个动作？** 说不出具体行为变化，就无法验收。
- **如果只能做完一半，哪一半最有价值？** 答不出，说明方案还是模糊的一大块。

## 二、成本-证据矩阵

过了门槛的，按两轴定位：

|  | 成本小 | 成本大 |
|---|---|---|
| **证据强（E1/E2）** | **快赢**：本轮做，通常立刻改善体验 | **主战场**：值得做，拆成可验证的小步 |
| **证据弱（E3）** | **顺手做**：最多 1-2 个，别用它填满迭代 | **先验证**：不直接做，先设计最小验证 |

四格都要能说清为什么落在这一格。落在"主战场"的，必须给出第一步小到可以在半天内完成。

### 验证难度（第三根轴，别忽略）

成本小不等于容易验证。改动便宜但验证不了的方案，做完只能靠感觉。

| 难度 | 判据 | 处理 |
|---|---|---|
| 易 | 当次就能重走路径、跑命令对比 | 可以直接做 |
| 中 | 要构造特定数据或场景才看得出效果 | 先写好观测方法，再做 |
| 难 | 需要真实用户长期使用才显现（留存、习惯） | 只做 L1 保护性改动，不把结论押在上面 |

验证难度为难的，必须配一个"当次可观察的代理指标"（见 06）。配不出来，就不是本轮该做的事。

## 三、减法优先

同一问题有多种解法时，按这个顺序选，前面的能用就不选后面的：

1. **删掉**（这个步骤/功能真的需要吗）
2. **合并**（两个入口能否变一个）
3. **改默认值**（能不能让用户不用选）
4. **自动化**（能不能让系统替用户做）
5. **改文案/顺序**（能不能只是说清楚）
6. **新增功能**（最后手段）

违反这个顺序时，必须在提案里说明理由。

## 四、提案条目格式

```
## 提案 N｜标题
来源：问题 #2 / 机会 #3
目标用户：谁在什么场景下受益
现状：[E1] 现在怎么做，代价是什么
方案：具体到能直接开工（改哪个文件/哪个流程/哪几个交互）
预期价值：改善什么，改善多少（可量化就用指标，不能就用可判断的现象描述）
证据与可信度：E1/E2/E3 + 一句话说明依据
成本：小(半天内) / 中(1-3天) / 大(3天以上或需重构)
风险：影响哪些现有能力、数据、使用习惯
定位一致性：四问结论（通过 / 第几问未通过）
不做会怎样：具体的损失
验证方式与难度：怎么判断有效 + 易/中/难
权限级别：L1 / L2 / L3
优先级：本轮 / 下轮 / 待验证 / 不做
```

## 五、排序与收口

排序依据：**影响 × 证据强度 ÷ 成本**，不搞精确打分。数量级判断足够。

**收敛的硬约束**（机械执行，不靠自律）：

- 本轮实施项 **≤ 3**，其中必须有且仅有 1 项是主目标。
- "不做清单" **≥ 1 条**，且每条有理由。
- 每个实施项都必须能回答"改完之后，重走哪条路径能看到差别"。
- 超过 3 项时，把预算外的最优项写进 Backlog 并注明"下轮首选"，不要挤进本轮。

对话里的收口规则：

- 给 **1 个推荐下一步** + 最多 **2 个备选**，其余进 Backlog。
- 推荐项要说明"为什么是它，而不是别的"。
- 明确列出"本轮不做"的项和理由——这比"要做什么"更能体现判断力。
- 如果结论是"暂时不需要改"，直接说，并说明什么条件下需要重新评估。

## 六、合法的"不做"结论

以下结论都可接受，且必须敢于给出：

- 现有方案已经够好，改了也不会更好。
- 这个问题真实存在，但影响面太小，不值得投入。
- 这个方向有价值，但当前证据不足，应先验证。
- 有更值得优先处理的问题。
- 用户提出的解决方式不是最优解，真正的问题是另一个（必须解释理由）。

最后一条尤其重要：用户说"给我加个新手引导"，可能是产品没有给出值得探索的理由。可以不同意，但要给出证据和替代方案，不能只是拒绝。

## 七、写入档案

- 采纳的进 `ITERATION_LOG.md` 计划区。
- 拒绝的进 `DECISION_LOG.md`，写清拒绝理由——防止下一轮重复提出。
- 待验证假设进 `OPPORTUNITY_BACKLOG.md`，重要者单独建 `hypotheses/<名称>.md`。
- 影响长期设计取向的，更新 `PRODUCT_PRINCIPLES.md`（需用户确认后才算数）。

## 退出条件

- [ ] 每个候选都过了三道门槛或写明卡在哪
- [ ] 计划里 ≤ 3 项进入本轮，且有明确的第一项
- [ ] 每项都有验证方式
- [ ] 有"不做清单"及理由
- [ ] 用户已确认实施范围（未确认则停在提案，不动手）

## 常见失败

- 列 12 条建议让用户挑 → 把判断工作推回给用户，等于没做。
- 全是低成本小改动 → 看起来交付很多，核心体验没动。
- 不写验证方式 → 无法进入 06 的验收，最后只能自评"感觉好多了"。
- 只提加法 → 功能越堆越多，复杂度上升。
