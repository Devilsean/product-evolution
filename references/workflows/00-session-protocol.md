# 00 会话协议（Session Protocol）

每次调用产品进化能力时，进入和离开都要走这里。目的是：**不重复分析、不重复提案、不丢结论**。

---

## 一、进入：S0 读档案（3 分钟内完成）

### 1. 判断是首访还是续跑

```bash
ls -1 product-evolution/ 2>/dev/null
```

- 目录不存在 → **首访**：跳到第三节。
- 存在但 PRODUCT_PROFILE 为空或只有模板 → **半首访**：按首访处理，但保留已有条目。
- 存在且有内容 → **续跑**：走下面的顺序。

**先看有没有未归档的 session**：`ls -1 product-evolution/sessions/` 里最新目录若缺归档表（上一轮异常中断），先把它的"未晋升"项读完，再决定是否沿用。这些是轮次现场，不是项目事实。

### 2. 按固定顺序读，不要全读

| 顺序 | 文件 | 只取什么 | 读多久 |
|---|---|---|---|
| 1 | `ITERATION_LOG.md` | 最近 2 轮的"目标 / 结论 / 遗留问题 / 下一轮建议" | 从末尾倒着读，够 2 轮即停 |
| 2 | `DECISION_LOG.md` | 所有"拒绝"条目 + 最近 3 条"采纳"条目的理由 | 只扫标题与理由 |
| 3 | `OPPORTUNITY_BACKLOG.md` | 状态为"待验证"的条目 | 只读标题与状态 |
| 4 | `PRODUCT_PROFILE.md` | 定位、目标用户、核心价值假设、验证能力、当前阶段 | 全读 |
| 5 | `PRODUCT_PRINCIPLES.md` | 全读（通常很短） | 全读 |

**不要重读上一轮的观察日志和完整诊断报告**，除非本轮要复现同一个问题。它们的信息已压缩进 ITERATION_LOG。

### 3. 生成两个东西（必须写出来）

**A. 已读摘要**（5 行以内，贴在回复开头）：

```
上轮：目标 X，结论 部分达成，遗留 Y。
已否决：A（理由）、B（理由）。
待验证：C、D。
当前阶段：MVP 可用 / 有留存。
本轮建议模式：专项（理由）。
```

**B. 禁止重复提案清单**：把 DECISION_LOG 里被拒绝的项和 Backlog 里正在验证的项列成标题清单。本轮任何提案若与其中一项实质相同，必须显式说明"与 X 相同，但前提 Y 已变化"，否则不许重新提出。

### 4. 检查档案是否可信

三处常见失真，遇到就地标注，不默默沿用：

| 症状 | 处理 |
|---|---|
| PRODUCT_PROFILE 的"验证能力"与本轮实际环境不符（换了机器/依赖坏了） | 更新该字段，并在回复中说明验证层级变化 |
| ITERATION_LOG 最后一轮写"达成"但没有证据字段 | 标记为"结论不可信"，本轮若涉及该区域需重新取基线 |
| 定位/用户与实际使用情况矛盾（用户自述已改变方向） | 先与用户确认，确认后更新 PROFILE 并写入 DECISION_LOG |

---

## 二、离开：S9 归档（三步，顺序不能换）

只写这次真正发生变化的内容，不整篇重写。分层规则见 `09-knowledge-boundaries.md`。

### 第一步：写 session（L3，必做）

新建 `product-evolution/sessions/<YYYY-MM-DD-HHmm>/session-log.md`，按 `templates/session-log.md` 填。**这一轮的所有观察、推断、假设、待决策提案先全部落在这里**，不直接写进 L2。

当前环境无写权限（Ask 模式 / 只读）时：把 session 内容作为回复的末节交付（标题"本轮现场（未落盘）"），并声明"下一轮开始时请先把这段内容补存到 sessions/"。声明未落盘不算违规，假装落盘才算。

每条记录首行带一个状态词，**默认 `candidate`**，不写理由（只有 `rejected` / `void` 补一行原因）。

只做了分析、没有实施的轮次，归档到此结束（第 2、3 步做空跑检查即可）。

### 第二步：晋升到 L2（够格的才搬）

| 文件 | 什么条件下写 | 写什么 |
|---|---|---|
| `DECISION_LOG.md` | **用户已明确定**（采纳或拒绝） | 日期 / 事项 / 决定 / 理由 / 状态（`confirmed` 或 `rejected`）。待回复的提案**不写这里** |
| `ITERATION_LOG.md` | 做过实施 | 按 `templates/iteration-report.md` 追加一轮 |
| `PRODUCT_PROFILE.md` | 定位、用户、能力、验证能力**真的**变了 | 只改对应字段 + 更新日期 |
| `PRODUCT_PRINCIPLES.md` | 用户明确确认了某条原则 | 必须写"用户确认于 YYYY-MM-DD"，未确认的不写 |
| `OPPORTUNITY_BACKLOG.md` | 有新假设，或有旧假设被关闭 | 新增/标 closed + 理由 |

搬走的内容，在 session 的归档表里标 `已晋升 → 文件名`；没搬的标 `未晋升 + 缺什么`，下一轮据此判断能否重提。

### 第三步：登记方法候选（L1，谨慎）

只有"可能通用"的经验才写，写进 `references/method-ledger.md` 的候选区：抽象表述 + 来源代号 + 缺口。**不得**因为"这次很有用"就改 SKILL.md 或 workflow 正文——那要过四道闸。

任何情况下都不写：技能包内的产品名、项目档案的方法论正文、未确认判断进 DECISION_LOG。三条硬线见 `09-knowledge-boundaries.md` 第三节。

---

## 三、首访：建档案

1. 先扫项目既有文档（`README*`、`PRD*`、`docs/`），能直接用的信息搬过来，不另造格式。
2. 建目录与五个文件，用模板填充。**允许大量字段是"未知（缺证据）"**——空着比编造好。
3. `PRODUCT_PRINCIPLES.md` 首访时通常写不了内容，保留模板并注明"待用户确认"。
4. `hypotheses/` 与 `evidence/` 按需创建：前者有跨轮假设时建，后者第一次截图时建。`sessions/<时间>/` 每轮新建。

```bash
mkdir -p product-evolution/sessions/$(date +%Y-%m-%d-%H%M)
```

不要覆盖项目已有的 README / PRD / 设计文档；档案是新增的平行记录，不是替代品。

---

## 四、跨轮衔接：让上一轮的结论真正被用上

每轮结束时回答三个问题，写进 ITERATION_LOG：

1. **遗留的那一个最重要问题是什么？**（只允许一个，多于一个说明没做取舍）
2. **下一轮最该先验证什么？**（一句话，具体到能开工）
3. **有没有结论被本轮推翻？**（有就更新 DECISION_LOG，注明翻案理由）

下一轮开始时，第一件事就是看这三个问题的答案，而不是重新分析一遍产品。

---

## 五、完成判据（本条协议本身）

进入侧：

- [ ] 已判断首访 / 半首访 / 续跑
- [ ] 已写出 5 行"已读摘要"
- [ ] 已生成"禁止重复提案清单"
- [ ] 档案失真项已标注

离开侧：

- [ ] 本轮已写 `sessions/<时间>/session-log.md`
- [ ] 够格的内容已晋升到 L2，session 归档表里每条都有去向
- [ ] 待用户回复的提案没有写进 DECISION_LOG
- [ ] 可能通用的经验已进 method-ledger 候选区（或判定为不通用）
- [ ] 遗留问题只有一个，且具体到能开工
- [ ] 若结论推翻了旧决策，DECISION_LOG 已注明翻案理由

## 六、档案反模式

- **只写不改**：每轮追加日志，但 PROFILE 永远停在第一次的状态 → 认知过期。
- **全量重写**：每次把 PROFILE 重写一遍，导致历史字段悄悄丢失。
- **写猜测**：把"我觉得用户可能想要"写进 PROFILE 的定位字段 → 后续所有判断被污染。
- **写成就**：ITERATION_LOG 只写"已完成优化"，不写证据 → 下一轮无法判断是否真的改善了。
- **不写拒绝**：只看采纳记录，导致同一方案被反复提出。
