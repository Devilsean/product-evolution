# 01 产品理解（Product Discovery）

目标：产出一份**能用来做判断**的产品认知，而不是对 README 的复述。

完成标志：能通过"三句话测试"——不看文档，用自己的话说清：

1. 这个产品为谁解决什么问题；
2. 它当前最强的一环是什么（有证据）；
3. 它当前最弱的一环是什么（有证据）。

任何一个说不出来，说明理解还不够，继续查。

---

## 采集顺序

按成本从低到高，不要一上手就读全部代码。**时间盒：首访 45-60 分钟，超时也要先出一版可用档案**，剩下的标"未知"。

### 1. 项目文档（5 分钟）

找：`README*`、`PRD*`、`DESIGN*`、`docs/`、`CHANGELOG*`、`*.md` 根目录文件。

只取四类信息：产品定位、目标用户、核心流程、已知限制。文档里其余内容先跳过。

注意：文档写的是**意图**，不是**现状**。两者不一致是常态，后面必须核对。

### 2. 代码结构（10 分钟）

用最少的信息还原"产品实际有什么":

- 入口与路由表（`src/pages`、`app/`、`routes`、命令注册）→ 用户可见的能力清单
- 数据模型（schema、migrations、types、models）→ 产品真正沉淀了什么
- 状态与存储（本地存储键、数据库表）→ 用户的投入存在哪
- 依赖清单（`package.json`、`pyproject.toml`、`requirements.txt`）→ 技术边界，以及"计划过但没做完"的痕迹

产出：**能力清单表**

| 能力 | 入口位置 | 文档提到 | 代码实现 | 用户能否发现 |
|---|---|---|---|---|
| 例：批量导出 | `src/pages/Orders.tsx:88` | 是 | 部分 | 隐藏在右键菜单 |

这张表是后面诊断"功能很多但没人用"的直接原料，值得认真填。

**非 Web 项目的对应物**（别去找 `src/pages`）：

| 形态 | 能力清单从哪来 |
|---|---|
| 桌面应用 | 主窗口菜单、托盘菜单、设置页；`main` 进程的 IPC 通道名 |
| CLI | `--help` 输出、子命令注册表、参数解析处 |
| 插件/扩展 | manifest 里的 commands / contributes 字段 |
| AI Agent | 工具注册表、prompt 模板、会话状态机 |
| 后端/API | 路由表 + 开放接口文档 |

### 3. 可运行性（10 分钟）

读 scripts 段，判断能否本地跑起来：

```bash
# 常见入口，挑存在的看
cat package.json | head -40
ls Makefile pyproject.toml docker-compose.yml 2>/dev/null
```

记录：启动命令、依赖是否齐全、是否需要密钥/外部服务、需要多长时间。

跑不起来不算失败，但要立刻记下"能验证到什么程度"。

### 4. 用户口述（如有）

问三个问题就够，别做问卷：

- 你最开始想做这个产品，是为了解决你自己的什么麻烦？
- 现在有真实用户在用它吗？他们最常做的是哪件事？
- 有哪些地方你自己用着也别扭，但一直没改？

用户的答案全部标 E2（自述），不要当 E1 事实。

### 5. 实际运行

交给 `02-experience-exploration.md`。本步只负责把入口和环境准备好。

## 三源核对

文档、代码、实际运行三者必然有差异。显式列出来，这是高价值信息：

| 事项 | 文档说 | 代码说 | 实际运行 | 结论 |
|---|---|---|---|---|
| 例：AI 草稿需用户确认 | 有确认流程 | 有 confirm 接口 | 自动入库，无确认提示 | 实现偏离意图（E1） |

三类差异各自的含义：

- **文档有、代码没有** → 规划未落地，或已废弃。不要当成缺陷，先问是不是刻意砍掉的。
- **代码有、文档没有** → 隐藏能力或实验残留。往往是"用户不知道产品能做到什么"的根源。
- **代码有、跑起来不对** → 功能缺陷，进诊断。

## 填写 PRODUCT_PROFILE

用 `references/templates/product-profile.md`。规则：

- 每个字段都要能指到证据；指不到的写 `未知（缺证据）`，不要用合理推测填空。
- "核心价值假设"单独标注 E2/E3，并写明"如果这个假设错了，产品会怎样"。这一条决定了后面所有提案的方向。
- "发展阶段"必须选一个，不能模糊。判据如下，选错会导致建议错位（给 MVP 提留存机制是浪费）：

| 阶段 | 判据 | 该阶段最该做的事 |
|---|---|---|
| Demo | 只有开发者自己能跑通，无真实用户 | 验证核心假设，不要做体验打磨 |
| MVP 可用 | 有真人能用完一次核心任务 | 缩短到首次价值的路径 |
| 有人重复使用 | 同一用户用过 ≥3 次，且是自发来的 | 修摩擦、补断点 |
| 有留存 | 用户会主动回来，有积累 | 深化价值、建立功能间联系 |
| 有增长 | 新增主要靠口碑/传播 | 降低新用户门槛、保护老用户体验 |
- "验证能力"字段记录本次能做什么验证（能不能起服务、能不能截图、能不能跑测试），后续所有"已验证/未验证"的声明都以它为准。

## 退出条件

- [ ] 能力清单表填完，条目数和代码里的入口数一致
- [ ] 三源差异表至少有一行（一行都没有，说明核对得不够细）
- [ ] 三句话测试通过
- [ ] PRODUCT_PROFILE.md 已落盘，未知字段已标注
- [ ] 明确知道下一步该走哪条模式

## 常见失败

- 把 README 翻译一遍就交差 → 没有新增认知，等于没做。
- 只读代码不看运行 → 会把"设计上支持"当成"用起来可以"。
- 一上来就提改进建议 → 违反铁律 1，且建议必然泛化。
- 用户没有 PRD 就卡住 → 没有 PRD 是常态，用代码 + 运行 + 提问补。
