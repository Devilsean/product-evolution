# 08 专项优化（Focused Improvement）

用于用户已经指出具体位置的情况：某个页面、某条流程、某个功能。

核心纪律：**只解决目标区域的问题，遇到范围外的问题记录不处理**。专项模式最常见的失败不是没修好，而是顺手改了一大片，最后说不清是哪一步起了作用。

诊断方法沿用 03，判断沿用 05，验收沿用 06；本文件只定义裁剪后的执行顺序和额外要求。

**最小读取集**（专项模式不必全读那三个文件）：02 只读 §一/§二/§三（探测、取证、剧本）；03 只读 §二/§三/§四/§六（分流、归因、定性、条目格式）；05 只读 §一/§四/§五（门槛、提案格式、收口）；06 只读 §三（分层验收）。其余按需。

---

## 步骤 1：把目标写成一句话（范围锁定）

不许用"优化一下结算页面"这种说法。写成可判定的形式：

```
目标：<用户动作> 从 <现状> 改善到 <可观察的状态>
不包含：<明确排除的相邻区域>
```

示例：

> 目标：新建报表 从"打开空白画布" 改善到 "能基于已有数据源一键生成初稿"。
> 不包含：数据源本身的编辑体验、报表正文的编辑器功能。

"不包含"这一行必须写。它决定了后面所有"顺手"的边界。

## 步骤 2：只采集目标区域的最小上下文（20 分钟）

不要重读整个项目。需要四样：

1. 目标区域的入口与组件（文件路径、路由）
2. 它读写的数据（字段、存储键、接口）
3. 它依赖的上游（用户到这里之前已经有什么）
4. 它影响的下游（改完会影响谁）

写成一张小表，作为后面判断"能不能只改这里"的依据：

| 层 | 涉及 |
|---|---|
| 入口 |  |
| 数据 |  |
| 上游 |  |
| 下游 |  |

若发现要改的东西超出了这张表（比如必须动数据模型），停下来说明，并按 SKILL.md 的规则决定是否升级为完整模式或 L2/L3。

## 步骤 3：走查目标路径并取基线（必须做）

按 02 的路线裁剪执行：改进流程走 **A(零状态) + C(异常) + E(组合)**；改进页面走 **C + D(可发现性) + 该页正常路径**。

**基线必须在改动前取。** 取不到基线，后面就无法证明改善。

量级豁免：改动是纯 L1 微调（改文案、调样式、改一个默认值，无流程与行为面变化）时，可免基线表，改为在 session 里记一行"改前现象"。判断标准：改坏了能否用一句话说清原状——能，就适用豁免。需要记时仍按下表：

| 指标 | 基线值 |
|---|---|
| 完成目标任务的步数 |  |
| 页面跳转次数 |  |
| 必须的输入项数 |  |
| 需要用户判断的次数 |  |
| 卡点数（犹豫/找不到/反复试） |  |
| 出错后的可恢复情况 |  |

取不到的情况（比如功能根本不存在）写"不存在"，并改用"用户现在怎么绕过去"作为基线。

## 步骤 4：诊断并锁定 1-2 个根因

按 03 做聚类与归因，但只针对目标区域。允许的结论包括：

- 根因不在目标区域 → 说明并给出该去的地方，**不动手**。
- 目标区域的问题有 3 个以上 → 只挑 1 个主因 + 最多 1 个附带，其余记 Backlog。

## 步骤 5：改，然后对比

改动范围必须与步骤 1 的"不包含"一致。改完立刻：

1. 重走步骤 3 的同一条路径，填同一张基线表。
2. 跑工程检查（构建/测试/类型）。
3. 判定三态：达成 / 部分达成 / 未达成。

前后对比是最低要求。没有基线就没有对比，只能写"改动已完成，效果未测量"——这是降级结论，要如实写。

## 步骤 6：越界登记

专项模式中任何"顺手发现但没处理"的问题，写进 OPPORTUNITY_BACKLOG，一行一条：

```
[专项越界] 描述 | 位置 | 证据等级 | 建议处理模式
```

不处理不是遗漏，是范围管理的正常结果。但要留痕，否则下一轮又会重新发现一遍。

## 退出条件

- [ ] 目标与"不包含"都已写明
- [ ] 基线与改后数据在同一张表里
- [ ] 工程检查有命令与结果
- [ ] 越界问题已登记
- [ ] 结论为三态之一，未达成未被美化

## 常见失败

- 顺手重构："既然都打开这个文件了" → 无法归因，且引入无关风险。
- 没取基线就改 → 只能靠感觉验收，等于没验收。
- 把"用户说的方案"直接当需求实现 → 用户说"加个引导"，可能真正的问题是流程太长。允许提出不同方案，但要给出证据。
- 改完只跑构建不重走路径 → 工程层通过不等于体验层改善。
