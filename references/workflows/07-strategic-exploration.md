# 07 方向探索（Strategic Exploration）

用于回答"下一步该做什么 / 要不要换方向 / 为什么没差异化"。

与完整模式的区别：**不追求修好所有问题，只判断值不值得换一条路走**。产出是 2-3 个可比较的方向，不是任务清单。

方向探索只提案，不动代码。任何实施都要回到 05/06。

---

## 前置

需要一份可用的 PRODUCT_PROFILE。若不存在，先做 **30 分钟简版理解**（不是完整 01）：

- 读 README/PRD 各一遍
- 列出路由/页面/命令 → 能力清单
- 确认能否运行
- 写清：为谁解决什么问题、现在实际在做什么、当前阶段

简版必须在回复里声明"定位认知基于文档与代码，未做实机走查"，且后续所有方向都标 E2/E3。

---

## 步骤 1：定位重审（15 分钟）

回答三个问题，每个都要落到具体句子，不许写形容词：

1. **产品自己认为它是谁？**（从 README/首屏文案抄一句原话）
2. **用户实际把它当什么用？**（从功能使用路径、issues、用户自述推断）
3. **两者是否一致？**

不一致有三种典型：

| 类型 | 表现 | 含义 |
|---|---|---|
| 说大做小 | 定位宏大，实际只完成了其中一小段 | 方向没错，价值没做完 → 走"深化" |
| 说小做大 | 定位是工具，实际被当工作台用 | 用户已经投票 → 走"顺势扩展" |
| 各说各话 | 定位与使用毫无关系 | 定位失真 → 需要重新定义，风险最高 |

这一步决定了后面方向的性质。跳过它会得到"什么都值得做"的结论。

## 步骤 2：局限扫描（20 分钟）

按六类结构性局限逐项检查，每类给出**具体证据**（不是判断）：

| 局限类型 | 检查问题 | 证据长什么样 |
|---|---|---|
| 形态局限 | 当前形态（网页/单机/单用户）是否限制了核心价值 | "必须整篇生成才能看效果，无法局部重写" |
| 流程局限 | 关键流程是否要求用户先付出大量投入 | "开始第一个任务前必须填 12 个配置字段" |
| 数据局限 | 产生的数据是否被浪费、是否无法复用 | "录入的明细从未被用于更新汇总口径" |
| 角色局限 | 是否假设了只有一种用户（一个人从头做到尾） | "无法把半成品交给同事接手" |
| AI 使用局限 | AI 是否只被当作"生成器"，而非协作者 | "AI 只能整段生成，不会指出与已有数据的冲突" |
| 价值表达局限 | 用户能否在 10 秒内知道这东西能干什么 | "首屏只有一个空项目列表" |

一个方向通常对应 1-2 个局限。找不到局限就不要提方向——那说明还只是在做体验优化。

## 步骤 3：生成三个方向（必须三条，且不同类）

强制结构，避免三个方向其实是同一个：

- **方向 A｜深化**：不做新东西，把现有价值做到位（对应"说大做小"）
- **方向 B｜扩展**：承接用户已经发生的行为，往外延一格（对应"说小做大"）
- **方向 C｜重构**：挑战当前形态，换一种方式交付同一价值

每条写成**方向卡**（缺项不算完成）：

```
## 方向 X｜一句话标题
类型：深化 / 扩展 / 重构
针对的局限：（来自步骤 2 的哪一条，附证据）
产品会变成什么样：一句话，让人能想象出来
用户的一天会怎么变：具体到动作
需要新做什么：
需要放弃什么：← 必须写，写不出说明没想清
为什么是我们能做：技术/数据/场景上的既有优势
最大风险：
反证条件：出现什么现象说明这条路不对
证据等级：E2 / E3
```

"需要放弃什么"是这张卡的核心。任何方向都要付出代价：放弃某个用户群、某个功能、某种简洁性。写不出代价的方向是不可信的。

## 步骤 4：比较与淘汰（15 分钟）

五维比较，不做精确打分，只做排序与淘汰：

| 维度 | 判断方式 |
|---|---|
| 价值上限 | 做成之后，产品是"更好用一点"还是"能做以前做不到的事" |
| 证据强度 | 有多少 E1 支撑，还是纯 E3 推演 |
| 成本 | 是否需要重构数据模型/核心流程（是 → 成本翻倍） |
| 风险 | 是否会破坏现有用户已建立的习惯与积累 |
| 可逆性 | 做错了能否退回（不可逆的方向要求更高证据） |

淘汰规则（任一命中即降级，不进入最终提案）：

- 三个方向本质是同一个 → 重做步骤 3
- 某个方向"需要放弃什么"写不出来 → 淘汰
- 纯 E3 且不可逆 → 只能作为"待验证假设"，不能作为推荐方向
- 方向实质等于"加一个功能" → 它不是方向，退回 04 当普通机会处理

## 步骤 5：战略提案

用 `templates/direction-proposal.md` 输出。要求：

- **一个明确推荐**，不是三条并列让用户选。
- 推荐必须包含"如果只做一件事，先做哪一步"——即最小可验证形态。
- 必须包含"维持现状的代价"：不换方向的成本是什么。用户常在"什么都不做"和"大改"之间漏掉这个选项。
- 明确写"这次不改代码"。

## 步骤 6：决策之后

**用户选"暂不改变"**：写 DECISION_LOG（含理由与重新评估的触发条件，例如"当出现 N 个用户抱怨 X 时重议"），本轮结束。这是合法且常见的结局。

**用户选某个方向**：不要直接开工。按顺序：

1. 把方向拆成 1 个最小可验证形态（通常是一次 L2，甚至一个假界面/手工流程）。
2. 回到 05 出提案，确认范围与验收标准。
3. 走 06 实施与验收。
4. 验收结论回写 DECISION_LOG：方向是否被验证，是否需要修正。

方向级改动若涉及定位/用户群/核心工作流 → L3，只提案不实施。

---

## 退出条件

- [ ] 定位三问已答，"一致 / 说大做小 / 说小做大 / 各说各话"已判定
- [ ] 局限扫描至少 2 类有具体证据（不是判断）
- [ ] 三个方向分属不同类，各写明"需要放弃什么"与反证条件
- [ ] 有一个明确推荐，且含最小可验证形态
- [ ] 写了"维持现状的代价"
- [ ] 明确声明本次不改代码
- [ ] 用户已选择方向或明确暂不改变，结论写入 DECISION_LOG

## 常见失败

- **三个方向都是一个方向的三种说法**：说明局限扫描没做，或只看到一种局限。
- **方向写成功能清单**："增加导入、增加模板、增加协作"——这是清单，不是方向。
- **只谈收益不谈放弃**：不可信，且实施时必然失控。
- **推荐一个不可逆的大改**：证据只有 E3 就推荐重构，是拿用户的产品赌博。
- **绕开"维持现状"**：不比较"不做的代价"，就无法判断是否值得动。
