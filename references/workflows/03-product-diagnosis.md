# 03 产品诊断（Product Diagnosis）

目标：从一堆现象里找出**真正值得解决的那几个**问题，并说清它们到底属于哪一类。

诊断阶段**不出方案**。出方案是 05 的事。提前给方案会导致所有问题都被改写成"加个功能"。

---

## 一、先聚类，不要逐条处理

把观察日志按"同一根因"合并。判断标准：

- 改一个地方能同时消掉 → 同一问题
- 出现在不同页面但是同一种毛病 → 同一根因
- 两条日志指向不同的可控层 → 不同问题

例：首页不知道下一步、新建表单不知道先填什么、导出按钮藏在二级菜单——三条日志都是"没有告诉用户该做什么/能做什么"，根因可能是**信息层级缺失**，一个改法能覆盖三处。

聚类后一般会从 20 条日志收敛到 4-8 个问题。多于 8 个说明聚类不够。

## 二、Bug 分流（第一道闸门）

先判断是不是 Bug。Bug 不进产品诊断，直接修；混进来会污染问题清单，也会打断观察。

| 判据 | 结论 | 处理 |
|---|---|---|
| 与产品自己的说明/常识不符：点了没反应、数据丢了、报错、算错结果 | **Bug** | 直接修或报告，不占诊断条目 |
| 行为符合设计，但做起来费劲、找不到、要反复试 | 体验问题 X | 进诊断 |
| 行为符合设计，但设计服务错了人 | 价值/定位问题 V | 进诊断，准备 L3 提案 |
| 行为正常，只是没做某件用户会想要的事 | 看有无场景证据：有 → 功能缺失 F；无 → 机会 O（E3） | 进诊断或 Backlog |

判不清时问一句：**"如果这行代码完全按设计运行，用户还会不满吗？"** 会 → 不是 Bug。

Bug 单独记：`[BUG] 复现路径 / 预期 / 实际 / 影响面`。同一次调用里先修 Bug 再分析产品，不要两件事交叉做。

## 三、五问归因

对每个聚类结果连续问"为什么会这样"，直到落到**你能改的那一层**：

| 可控层 | 说明 | 典型改法 |
|---|---|---|
| 文案与提示 | 说了什么、没说清什么 | 改措辞、加一句约束说明 |
| 交互与反馈 | 操作后有没有回应 | 改状态、加反馈、改默认值 |
| 信息架构 | 能力放在哪、如何被发现 | 调整层级、合并入口、改导航 |
| 工作流 | 完成任务的步骤顺序 | 合并步骤、去掉必须手填的环节 |
| 数据模型 | 有什么、缺什么、能否关联 | 补关联、补字段、补复用 |
| 产品定位 | 到底为谁做 | L3，只出提案 |

示例：

> 现象：新建报表后是空白画布，不知道先做什么。
> 为什么？→ 没有前置结构。
> 为什么没有？→ 报表和数据源没有强制关联，用户可以不选数据源直接画。
> 为什么允许？→ 产品假设用户已有明确的取数口径。
> 这个假设对目标用户成立吗？→ 不成立，目标用户是"有分析需求但不懂 SQL"的人。
> 归因：**产品定位假设与实际用户不匹配**（L3 信号），但可先在工作流层做低风险改法：新建报表时提供"从数据源生成 / 空白开始"两个入口。

注意最后那一步：能落到低风险层就先落，不要一上来就动定位。

## 四、四类定性

| 类型 | 判别问题（用它来分，不要凭感觉） | 提醒 |
|---|---|---|
| **功能问题（F）** | 用户想做的事，产品是否有入口？有入口是否完整？ | 先确认是"没做"还是"刻意不做" |
| **体验问题（X）** | 能做，但要不要多走几步、多想几次、多猜几回？ | 最常见，也最容易被加功能掩盖 |
| **价值问题（V）** | 做完了，用户得到的东西值得这些投入吗？他为什么要做这件事？ | 优先级通常最高，也最常被误判成 X |
| **机会（O）** | 现在没人提出不满，但换一种做法会明显更好？ | 不是问题，别写成缺陷 |

判不清时写"待澄清"，并列出还需要什么信息。硬塞进某一类会造成误判。

**特别注意**：把 V 类误判成 F 类（"价值没传达"被当成"缺个引导弹窗"），是本 Skill 最常见的整体性错误。遇到"用户不知道怎么用"时，先问是不是**产品本身没给出值得用的理由**。

---

## 五、影响评估

每个问题写三项，不要用"严重影响体验"这种话：

- **谁**：新用户 / 常态用户 / 重度用户 / 特定场景用户
- **频率**：每次必遇 / 特定路径才遇 / 偶发
- **代价**：放弃任务 / 多 N 步 / 误解并产生错误结果 / 只是不爽

"放弃任务"和"只是不爽"相差一个数量级，必须分开。

## 六、输出条目格式

整体报告按 `references/templates/experience-report.md` 组织，单条问题用下面的固定结构：

```
## 问题 N｜一句话标题
类型：X 体验问题
现象：[E1] 最短复现路径（3 步以内说清）
证据：[E1] src/pages/Chapter.tsx:120 / 截图 / 命令输出
根因假设：落在「工作流」层——报表创建不依赖数据源，用户被迫空想
影响：新用户，首次创建必遇，代价=放弃任务（3/5 位模拟用户在此中断，标 E3）
可改进空间：中（可局部改，无需重构数据模型）
是否值得改：待 05 判断
```

**两条硬规则**

1. **不能复现的现象不算问题。** 只出现过一次、说不清路径的，写进 OPPORTUNITY_BACKLOG 并注明"未能复现 + 观察到时的环境"，不进问题清单——否则后面的验收会以它为依据，永远无法关闭。
2. **诊断里不许出现方案。** 逐条检查：条目里若有"应该改成…""建议加一个…"，说明已经越界，删掉，留到 05。允许写的只有"可改进空间"这一档，用来给后面的排序留余地。

## 七、减法检查

诊断收尾时专门过一遍：

- 有没有功能从头到尾没人在主流程里用到？
- 有没有两个功能做的是同一件事？
- 有没有必须手动做的步骤其实可以自动完成？
- 有没有为了"看起来完整"而存在的模块？
- 有没有游戏化/统计/装饰性内容对核心价值没有贡献？

有就单独列成"减法候选"，与问题清单并列，进入 05 评估。减法项往往比新增项的投入产出比更高。

---

## 退出条件

- [ ] 问题数收敛在 4-8 个，每个都有 E1 证据或明确标 E2
- [ ] 每个问题都有类型、根因层、影响三项
- [ ] 至少一条减法候选（没有则说明理由）
- [ ] 没有把任何一个问题直接写成"应该加一个功能"

## 常见失败

- 一个问题拆成五条，看起来问题很多 → 无法排序，也无法验收。
- 根因停在"因为设计得不好" → 不可执行，必须落到具体可控层。
- 把所有问题都判成 F 类（缺功能）→ 会导致方案全是新增。
- 只诊断不筛选，把 20 个问题原样抛给用户 → 用户无法决策，等于没做判断。
