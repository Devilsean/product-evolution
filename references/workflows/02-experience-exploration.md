# 02 实际走查（Experience Exploration）

目标：用真实操作得到第一手事实（E1）。这是整个 Skill 最不可省略的一步。

反面模式：读代码想象用户感受 → 得到一堆"大概会困惑"的猜测。这不算走查。

**范围裁剪**：完整模式走全部五条路线；专项优化模式只走与目标相关的 2-3 条（改进某个流程至少走 A + C + E，改进某个页面走 C + D + 该页的正常路径），并在报告里写明"本次只覆盖目标区域，未做全局重新诊断"。

---

## 一、先探测验证能力

动手前先确认这个环境能验证到哪一层，把结论写进 PRODUCT_PROFILE 的 `## 验证能力`。

按顺序试，能到哪层算哪层：

| 层级 | 判断方法 | 得到什么 |
|---|---|---|
| L-a 真实界面 | 能起本地服务 + 有浏览器控制/预览/截图能力 | 视觉、状态、交互反馈的完整事实 |
| L-b 半实机 | 能起服务但只能看输出/日志/接口返回 | 数据流、状态变化、错误信息 |
| L-c 可执行片段 | 能跑 CLI、单元测试、脚本 | 核心逻辑的正确性与边界行为 |
| L-d 静态 | 都不能跑 | 只能读代码，所有体验结论降级为 E2 |

做什么：

```bash
# 1. 看启动方式
cat package.json 2>/dev/null | grep -A15 '"scripts"'
ls -1 Makefile docker-compose.yml pyproject.toml index.html 2>/dev/null

# 2. 尝试启动（能跑就跑，跑不起来立刻记原因，不要反复折腾）
npm run dev    # 或 python -m xxx / go run . 等

# 3. 起得来再确认端口，然后用当前可用的浏览器/预览/截图能力打开
```

如果环境提供浏览器控制能力，用它：打开页面、点击关键按钮、截图、读控制台。没有就退到 L-b/L-c，并明确声明。

**必须声明**：本次走查覆盖了什么、没覆盖什么。写法示例：

> 覆盖：核心业务流程（登录→筛选→批量处理→导出，共 11 步），空状态与错误路径。
> 未覆盖：多人协作、导出到第三方格式（需外部服务，本地无法验证）。

不许出现"我已全面体验产品"这种无依据的断言。

## 二、启动与取证（具体操作）

### 1. 启动

用项目自己的启动方式，不要自创：

```bash
# 先看它自己怎么启动
cat package.json | sed -n '/"scripts"/,/}/p'
# 按需依次尝试
npm run dev        # 失败 → npm run build 后本地起静态服务 → 直接打开构建产物
python -m <module> # Python 项目
```

后台启动，**用探测代替等待**：

```bash
curl -sS -o /dev/null -w "%{http_code}\n" http://localhost:5173 || echo "not up"
```

起不来时不要反复折腾依赖。先判断卡在缺依赖、缺密钥、还是需要外部服务，记一句原因就降级。

### 2. 数据隔离（最容易被忽略）

走查会污染用户数据，也会让"零状态"根本不可能。先隔离再动手：

| 存储 | 隔离方式 |
|---|---|
| Web 本地存储 | 无痕窗口 / 换端口（origin 不同即隔离）/ 换浏览器 profile |
| localStorage / IndexedDB | devtools 清空，或 `--user-data-dir=/tmp/walkthrough` 起一个干净 profile |
| 本地数据库 | 复制一份再改：`cp app.db /tmp/walkthrough.db`，用副本跑 |
| 云端数据 | 不用真实账号；注册测试账号，或指向本地 mock |
| 文件型产物 | 在临时目录里操作，不动用户真实项目目录 |

不隔离的后果：既破坏用户数据，又拿不到真正的"新用户第一次"体验。

### 3. 取证

- 截图存 `product-evolution/evidence/`，命名带序号与含义：`03-empty-editor.png`
- 每张截图配一行说明；**没有说明的截图不算证据**
- 控制台错误、失败请求（状态码 + 响应片段）必须抄进日志
- 每观察到的事实都要能在报告里回到具体位置

### 4. 降级阶梯

| 层级 | 拿不到界面时怎么做 | 仍能证明什么 |
|---|---|---|
| L-a 真实界面 | 浏览器打开、点击、截图 | 完整体验事实 |
| L-b 半实机 | `curl` 打接口 / 读运行日志 / 直接查数据库 | 数据流是否正确、错误是否被处理 |
| L-c 片段 | 跑单测、CLI、脚本，构造输入 | 逻辑与边界行为 |
| L-d 静态 | 只读代码与类型定义 | 设计意图，**不能证明体验** |

每降一级，结论可信度降一档；报告中标注等级，不得跨级宣称。

## 三、任务剧本（别把走查做成浏览页面）

"走查"不等于把每个页面点一遍。按剧本执行：每条剧本是一次完整任务，有起点、有终点、有成功判据。

至少跑三条基础剧本：

| 剧本 | 起点 | 终点（成功判据） | 记什么 |
|---|---|---|---|
| T1 首次完成 | 全新数据、什么都不懂 | 完成一次核心产出（提交一笔订单 / 导出一次 / 生成一份报告） | 步数、卡点、第几步看到价值 |
| T2 修改已有成果 | 已有 T1 的产物 | 改掉其中一个细节并确认生效 | 是否被迫重做整件事、能否局部改 |
| T3 中断与恢复 | 任务做一半 | 关掉再回来能接着做 | 状态是否保住、丢了多少 |

AI 类产品加两条：

| 剧本 | 要观察的 |
|---|---|
| T4 推翻 AI 产出 | 不接受生成结果时，能否只改一处、保留其余 |
| T5 一致性 | 录入新内容时，产品是否知道并提醒与既有数据的冲突 |

记录格式：`起点 → 动作序列（编号）→ 结果 → 判定（通过 / 受阻 / 放弃）`。

写不出终点（不知道怎么算完成）本身就是发现：说明产品没有明确的任务闭环。

## 四、观察日志（边操作边记）

格式固定，一行一条，观测与推断分开：

```
[E1] 打开首页 → 空白，只有一个"新建项目"按钮，无任何示例或说明。停留 8 秒不知道第一步做什么。
[E1] 点"新建项目" → 直接跳到一个空编辑器，标题为"未命名"。没有让我选模板或示例。
[E2] 这里可能需要先建数据源再做报表，但界面没有任何顺序提示。← 推断，未证实
```

规则：

- E1 只写"我做了什么、看到什么"，不写心理活动判断。
- E2 写推断，必须单独一行并标记。
- 记录时间/步数：完成一件事按了几次、跳了几个页面。数字比形容词有用。
- 记下每一次"我犹豫了"的瞬间——那是最有价值的信号。

## 五、五条走查路线（每条都走）

### A 新用户零状态

清空本地数据或用全新的存储位置，从打开产品到完成一次核心任务。

记录：总步数、必须看文档才能继续的地方、第一次看到"产品价值"的位置（第几步）。
如果 5 步内感受不到价值，这就是价值交付问题，不是引导问题——别急着加引导页。

### B 回访用户

模拟第二次使用：已经有数据、有历史。关注：能否快速回到上次的位置、重复劳动有多少、是否越用越顺手。

### C 边界与异常

逐个试：空输入、超长输入、特殊字符、重复提交、中途取消、误删、断网或接口失败、并发操作。

关注的不是"会不会崩"，而是**崩了之后用户知道发生什么、能怎么救**。

### D 能力发现

不看文档，只靠界面，找三个已知存在的能力（从能力清单表里挑最不显眼的三个）。

找不到就是可发现性问题，且是 E1 证据。这条几乎每次都能查出东西。

### E 组合路径

把两个以上功能连起来用。例如：导入数据 → 校验 → 生成报表；下单 → 支付 → 开票。

关注：数据是否自动流通、是否需要重复录入、A 的产物能否直接成为 B 的输入。

功能之间的断点，通常就是差异化的机会所在。

## 六、竞品视角（按需）

只在需要判断"这是不是行业通病"或"有没有更好的做法"时做。

做法：

1. 用检索工具找同类产品的**具体机制**，不是营销文案。
2. 只记录能验证的事实，附来源。
3. 检索不到就写"未获得可靠信息"，不要用印象补。

输出三列即可：

| 同一任务 | 竞品怎么解 | 我们的做法 | 差异是优势还是劣势 |
|---|---|---|---|

竞品研究的用途是**校准**，不是抄袭。看到竞品有而我们没有的东西，先问"我们需不需要"，再问"要不要做"。

---

## 七、角色模拟的边界

可以扮演三类用户去找线索：完全新手、每天用的重度用户、要交付给他人的专业用户。

但必须遵守：

- 产出一律标 **E3**，措辞用"如果……可能会……"。
- 明确写一句"以下为角色模拟推演，非真实用户反馈"。
- 不得把模拟结论写进 PRODUCT_PROFILE 的事实字段。
- 不得用它替代真实用户验证，也不得在验收时拿它当证据。

## 退出条件

- [ ] 五条路线都走过，或明确说明哪条没走及原因
- [ ] 观察日志 ≥ 15 条 E1，覆盖至少一条完整核心链路
- [ ] 每条 E1 都能复现（写清最短复现路径）
- [ ] 覆盖边界已声明
- [ ] 已选出 3-5 个最痛的观测点，交给 03 做归因

## 常见失败

- 只走主流程，不走空状态和错误路径 → 漏掉一半问题。
- 用"体验比较流畅"这类词总结 → 无法验证、无法验收。
- 把跑不起来当借口直接跳到读代码 → 应退到 L-c/L-d 并声明，而不是跳过。
- 一次走查记录 50 条，不分主次 → 后面无法收敛，应控制在 20 条以内并标出最痛的 3-5 条。
