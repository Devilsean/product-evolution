# 框架：优先级与取舍（Prioritization）

何时读：05 工作流执行时。目标是做出**能解释的取舍**，不是算出精确分数。

---

## 一、默认流程

```
候选 → 三道硬门槛 → 成本-证据矩阵 → 减法优先校验 → 排序 → 收口
```

### 三道硬门槛

| 门槛 | 不通过的处理 |
|---|---|
| 有真实问题或机会的证据？ | 进 Backlog，标"待验证" |
| 让产品更接近核心价值？ | 标 L3 提案，不进本轮 |
| 能说清怎么验证有效？ | 补验证设计，或降级为"探索" |

### 成本-证据矩阵

|  | 成本小 | 成本大 |
|---|---|---|
| **证据强** | 快赢，本轮做 | 主战场，拆小步做 |
| **证据弱** | 最多做 1-2 个 | 先验证，不直接做 |

### 减法优先校验

同一问题的多个方案，按 删 → 合 → 默认值 → 自动 → 文案 → 新增 排序取最先可行的。违反时写理由。

## 二、打分（可选，仅当需要比较 5 个以上候选时）

不要用复杂公式。三个因子各 1-3 分即可：

- **影响**：1=小幅不便，2=明显摩擦，3=导致放弃任务或产生错误结果
- **证据**：1=E3，2=E2，3=E1
- **成本**：1=大，2=中，3=小（注意方向）

排序值 = 影响 × 证据 × 成本。分数只用于排序，不作为说服依据；两项分数接近时，选用户价值更直接的那个。

**验证难度不进分数，但会改结论**：易验证的项可以直接执行；难验证的项（需要长期使用才显现）即使影响大，本轮也只做其中"当次可观察"的那一部分，其余标"待观察"。原因很简单——做完无法判断对不对的改动，风险无法关闭。

## 三、说"不做"的四种正确方式

| 情形 | 说法 |
|---|---|
| 问题真实但影响小 | "这个问题存在，但只在 X 场景出现，代价是多两步操作。建议记账不做。" |
| 方向对但证据不足 | "方向可能对，但现在只有推断。建议先做最小验证（半天），再决定投入。" |
| 与定位冲突 | "做了会让产品更像 Y 而不是 Z。如果确实要转向，这属于 L3，需要单独决策。" |
| 已经被否决过 | "这个方案在 2026-XX 讨论过，当时否决理由是……除非前提变了，否则不建议重复投入。" |

## 四、反模式

- **清单式交付**：给 10 条建议让用户自己排。这是把判断工作退回给用户。
- **全选快赢**：一堆低成本改动，看起来很忙，核心体验没动。
- **成本低估**：只算写代码时间，不算测试、文档、后续维护、用户重新学习。
- **沉没成本绑架**："这个模块已经做了，所以应该继续加功能。" 已投入不是继续投入的理由。
- **指标替代价值**：为了让数字好看而加机制，属于减法候选。

## 五、收口模板

```
本轮建议：<1 条>，因为 <一句话理由>。
备选：<最多 2 条>。
本轮不做：<列 2-3 项 + 各自理由>。
需要你决定：<如果有 L2/L3，明确列出等确认的点>。
```
