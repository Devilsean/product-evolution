# Product Evolution — 产品进化与体验优化技能

一个让 AI 真正帮你打磨产品的 Skill。

它管的不是"从 0 做1个功能"，而是"功能已经能用，但还不够好"之后的那一段：找出值得改的地方，改掉，并拿出证据证明改对了。允许的结论包括"这里不需要改"。

## 为什么不是"直接问 AI"

直接问"帮我优化一下这个产品"，通常会得到一份换到任何产品上都成立的建议——加引导、加提示、加仪表盘。看着都有道理，做完核心体验没变。这个 Skill 用机制拦住这类输出：

| 直接问 AI 的常见结果 | 本 Skill 的对应机制 |
|---|---|
| 没用过产品就给建议 | **先走查，再判断**：必须实际跑通主流程，留下 ≥15 条一手观察；跑不起来必须声明降级到哪一层，不许假装体验过 |
| 泛泛而谈，无法落地 | 每条判断带**证据等级**（E1 观察 / E2 推断 / E3 假设）；根因必须落到能改的那一层（文案 / 交互 / 信息架构 / 工作流 / 数据模型 / 定位） |
| 建议全是加法，越改越臃肿 | **减法优先**：删 → 合并 → 改默认值 → 自动化 → 改文案 → 新增，按这个顺序选解法，跳序要写理由 |
| 12 条建议让你自己挑 | **强制收敛**：一轮实施 ≤3 项、有且仅有 1 个主目标、必须附"不做清单"及理由 |
| 改完自己宣布成功 | **四层验收**（工程 / 体验 / 产品 / 真实用户），结论只有达成 / 部分达成 / 未达成三态，拿不出前后对比只能如实写"效果未测量" |
| 每次对话都从头分析一遍 | **跨轮记忆**：项目档案记录定位、决策、机会、迭代与被否决项，下一轮先读档案——不重复分析，不重提已拒绝的方案 |
| 一个项目的结论被带到所有项目 | **三级知识隔离**：通用方法、项目认知、本轮会话分层存放；单项目经验要升为通用方法，必须过抽象 / 范围 / 验证 / 登记四道闸 |

## 快速开始

### 1. 安装

把本目录整体复制（或链接）到 Agent 的技能目录：

```bash
cp -r <本目录> ~/.workbuddy/skills/product-evolution/
```

用目录链接（Windows Junction / macOS、Linux 软链）指向源码目录时，改源码即生效，不会出现副本漂移。

### 2. 调用

不需要记命令，对 Agent 说意图即可：

| 你想做什么 | 直接说 |
|---|---|
| 全面体检 | "帮我看看这个产品，做一次体验审计" |
| 卡住了 / 没方向 | "这个产品下一步该做什么"、"感觉没什么差异化" |
| 局部优化 | "这个新建流程太绕了，帮我看看" |
| 减法 | "功能太多了，想简化" |
| MVP 之后 | "MVP 做完了，接下来呢" |

也可显式指定：`完整模式` / `专项优化：<位置>` / `方向探索模式`。判定不清时，Skill 会问一句"你能指出具体位置吗"，据此分流。

## 三种模式

| 模式 | 什么时候用 | 会做什么 | 会动代码吗 |
|---|---|---|---|
| 完整进化 | 首次接触且想整体看一遍、要全面体检 | 理解 → 走查 → 诊断 → 机会 → 计划 → 实施一项 → 验收 | L1 可做，L2 需确认 |
| 专项优化 | 你能指出具体页面 / 流程 | 锁范围 → 取基线 → 归因 → 改 → 前后对比 | L1 可做，L2 需确认 |
| 方向探索 | 问下一步 / 要不要换路 | 重审定位 → 扫结构局限 → 三个方向 → 比较 → 提案 | 只提案 |

权限约定：L1 小改动直接做；L2 先提案、你确认后动手；L3（涉及定位、用户群、核心工作流）只出提案。

## 一轮下来你会得到什么

1. **产品认知档案**——定位、用户、能力清单、验证能力，每个字段都能指到证据
2. **体验与诊断报告**——按任务链路组织的问题清单，每条都有最短复现路径、根因层和影响面
3. **机会清单**——含至少一个跳出当前形态的方向，每张卡片带反证条件（出现什么现象说明它是错的）
4. **能拍板的计划**——≤3 项、有优先级、有不做清单，说不清验证方式的不会出现
5. （你确认后）**一次可验收的改进**——改前 / 改后同一张表对比，结论三态之一
6. **一个会积累的项目档案**——下一轮从这里继续，而不是从零开始

## 它会在项目里留下什么

在被分析项目根目录建 `product-evolution/`：

```
PRODUCT_PROFILE.md      产品认知档案（定位、用户、能力、验证能力、上轮结论）
PRODUCT_PRINCIPLES.md   已确认的设计原则（须带确认日期，未确认不写）
DECISION_LOG.md         已决定的事（采纳 / 拒绝；待回复的提案不写）
OPPORTUNITY_BACKLOG.md  机会与假设（未确认的默认标 candidate）
ITERATION_LOG.md        每轮改了什么、怎么验收的
hypotheses/             需跨轮跟踪的假设（按需创建）
sessions/<时间>/        本轮工作现场：观察、临时判断、待决策提案
evidence/               走查截图与日志（有截图时创建）
```

进入时先读档案；离开时先写 session，再把够格的晋升到正式档案——这是它不重复劳动、也不把猜测当事实的原因。

## 关键约束

- 没走查主要流程不出提案；跑不起来时降级并逐条标"未实机验证"
- 每个输出带"未验证声明"：没验证什么、为什么、什么条件下能验证
- 诊断阶段不出方案（防止所有问题都被改写成"加个功能"）
- 模拟用户的推演标 E3，不得充当验收证据

## 已知边界

- 真实用户层只能给验证方案，不能给结论——能力边界，不是缺陷
- 竞品研究是轻量做法（校准用），未做深度研究的独立工作流
- 完整模式成本高，同一产品短期内不建议重复跑
